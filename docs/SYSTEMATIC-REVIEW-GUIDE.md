# 系统性架构与正确性审查指南

本指南由根目录 [AGENTS.md](../AGENTS.md) 引用，供开发者和 Agent 重复使用。
起点是针对 v1.6.0 的审查建议；每次审查必须重新记录实际版本与 commit。
本文定义审查方法，不证明当前实现已满足这些要求，也不预先批准任何重构或迁移。
产品定位、用户当前确认的意图与产品交付原则以根目录 AGENTS.md 为准。

## 1. 范围与完成事件

先写：谁在什么场景需要什么结果、当前可能受到什么误导、修复后能看到什么、如何验收。
典型完成事件包括：旧资金流不再显示为今日值；排名清楚说明共同窗口和缺失标的；
模拟不会用尚未实现的收益给下一笔交易分配资金；固定版本安装不因网络故障改变来源。
这些是验收方向，不能直接当作已证实缺陷。

系统性审查覆盖四个领域，并沿用户入口 → Agent/MCP 或 API → Service → 缓存/fallback
→ 数据源与数据库追踪相关链路；研究链路还需追到计算和结果解释，发布链路追到正式安装产物。
局部审查只展开相关领域，说明排除项及原因。只有证据显示同类缺陷可能外溢时才扩大范围。
不以文件数、抽象数、测试数或修复 issue 数代替用户结果。

## 2. Audit：建立证据

记录基准版本、commit、工作区差异、审查范围、运行环境与证据类型：代码检查、离线复现、
集成观察、网络探针或文档声明。不得将旧报告的复现结果视为本次验证。

从实际调用方确认参数是否完整传递、字段含义是否一致、错误与质量信息是否丢失。
检查数据源转换、缓存键、增量写入、服务计算、工具输出和用户展示；不能只检查接口存在。
发现重复逻辑或耦合时，先说明其如何影响当前用户结果，再判断是否需要改变职责边界。

每项重要发现采用以下记录：

| 字段 | 必须回答的问题 |
|---|---|
| 状态 | 已证实缺陷 / 条件性风险 / 待验证假设；不要混写 |
| 触发与复现 | 最小输入、时间与配置、真实入口、预期和实际结果；提供可执行命令或样例 |
| 用户影响 | 哪个结果错误或误导、严重程度及依据、受影响调用方 |
| 根因与证据 | 文件与行号、调用链、被破坏的不变量；尚未证明的部分 |
| 测试缺口 | 现有测试为什么没覆盖；未检查时明确写待核查 |
| 兼容性 | 公开接口、配置、旧数据和已有报告的影响 |
| 最小行动 | 修复、限制计算、披露、改名或继续验证；验收方式 |

按静默错误及用户影响、依赖关系、成本排序。纯维护收益可延后，并写重新考虑的条件。

## 3. 四个领域的审查要求

### Market Time：信息何时发生、归属、可见和使用

分清事件时间、交易日/时段、信息可用时间、抓取/观察时间和结果截止时点。
UTC 存储不等于交易日语义已正确；抓取时间不等于事件时间或历史可用时间。
检查现有 A 股、美股的时区、假期、夏令时、午休、K 线起止标签、周期完成状态和交易日窗口；
其他市场在实际支持范围内检查，不以本文推导新的市场支持承诺。

关键约束：

- 同一事件经过适配、缓存、服务与展示后归属同一市场交易日；机器时区不改变研究结论。
- 盘中未完成 K 线不能静默作为完整周期输入；交易所收盘不等于供应商已完成发布或修订。
- 历史决策只用当时可获得的信息；确认信号产生、可以观察和可以成交的时间分别定义。
- 财报发布时间、修订版本及复权数据的事后变化需要单独核查。今天下载的历史数据不自动
  具备 point-in-time 有效性；缺少历史快照时披露无法还原，不能靠补时间字段声称已经解决。

优先复用已有时间规则；只有多个真实路径需要同一语义时才提议共用日历或时钟。

### Data Quality：返回数据是什么，是否可用

检查完整成功、部分成功、确认空结果、获取/解析失败、过期缓存与混合来源是否可区分。
失败不能静默变为零成交、零资金流或其他具有业务含义的值；保留旧数据需要保留其真实日期
并披露降级。既要保旧，也要避免将旧值解释为最新值。

检查必要元数据能否追踪：provider、抓取/验证时间、数据截止、请求与实际覆盖、复权、币种、
单位、转换/估算/拼接及缺失原因。按请求或批次保存也可，不要求每条记录复制所有字段。
共享对象的“最近一次状态”须验证在并发和批量调用中是否仍对应本次结果。

关键约束：

- 缓存增量更新和回填幂等，不丢失既有区间，不产生重复；部分写入和并发失败可恢复。
- fallback 不能静默改变复权、单位、时间语义；混合标签必须被下游理解，存在标签并不足够。
- 日线、分钟线与未完成周期采用适合各自语义的更新规则；历史复权价格不能假定永久不变。
- 质量信息到达衍生计算、Agent/MCP 和用户结果；按具体计算定义正常、降级披露或拒绝政策。
  不使用一个通用覆盖率阈值替代截止日、窗口、口径与缺失分布检查。

### Quantitative Validation：计算、研究与执行分别验证

公式正确只证明计算正确。历史实证需要数据与方法成立，执行评估还需要现实交易约束。
审查前视、幸存者、样本选择、多重检验、不同步数据和事后修订偏差，包括 Agent 研究工具。

关键约束：

- 信号产生、成交价格、开平仓、持有周期、资金占用与收益入账的时点明确。
  重叠持仓不提前释放资金，不提前复用未来收益；顺序遍历信号本身不能证明无前视。
- 组合净值、回撤和夏普使用一致的时间序列与年化依据；成本、滑点、流动性及交易限制的
  已建模与未建模项分别说明。交易级收益汇总不得冒充严格组合回测。
- 跨标的比较采用可解释的共同截止、历史窗口、样本集合和单位；不同步、缺失和样本池变动
  有明确处理政策。收益强弱或排名变化不能直接解释为资金流入。
- 使用手算参考、固定数据回放、缺失/扰动/边界输入和因果测试验证根因。
  预测能力声明还需样本、基线、样本外评估、成本/参数敏感性与统计不确定性证据。

结果按证据描述为探索性、计算与数据语义已验证、完成历史实证评估或完成执行约束评估。
如采用 Experimental / Mechanically Validated / Empirically Evaluated / Execution Evaluated
标签，必须同时给出适用数据、参数、样本、验证版本、限制和证据；它们不是盈利认证。
不要求所有探索性指标先完成完整回测，但必须诚实命名。

### Release Integrity：发布和研究结果可追踪

以根目录发版规则、当前 CI 和发布脚本为事实依据，先盘点已有检查再补缺口。
核查 tag、包元数据、前端资源、Skills/MCP、安装器及实际发布的 Docker 产物之间的绑定。
只检查项目实际支持和分发的形式，不因清单扩大发布矩阵。

关键约束：

- 固定版本请求不能静默转为浮动分支；解析失败时的行为明确，默认 latest 与固定版本区分。
- 正式安装后必需资源和入口可用，依赖策略可解释；源码通过测试不等于安装产物通过。
- 区分静态、单元、集成、跨模块契约、迁移、安装升级、网络探针和发布后 smoke 的证明范围。
- 数据变更先评估旧版本读写兼容、失败恢复与回滚；代码回滚不自动等于数据回滚。
- 重要研究结果保留足够的软件/计算版本、参数、数据来源与截止、输入快照或数据版本、
  质量说明与生成时间。相同输入应得到一致结果；仅有相同参数而重新请求外部数据不保证复现。

## 4. Design → Implement：只建设必要支持

设计围绕已证实的问题与用户完成事件。比较局部修复、复用现有组件、增加共用契约，说明选择、
复杂性成本与兼容策略；无需为每个局部修复独立写 RFC。共用抽象应减少实际重复与语义分歧，
不能只把复杂性搬到新层。优先交付小规模纵向修复，再处理其依赖模块。

每个阶段写明用户产物、前置条件、修改范围、验收、风险与延期条件。
审查授权不自动包含实现；已有实现授权继续有效，不因本指南新增重复确认。
涉及存量金融数据改写、键或复权语义变化、数据库迁移时，先提供影响范围与验证证据，
评估预检查、备份、失败中断恢复、回滚/旧版本读取及既有报告是否需重算或标记。
验证应使用临时数据库或脱敏副本，不能用用户数据库试验破坏性操作。

## 5. Validate：不变量、根因测试与用户验收

以下是测试设计矩阵，不表示现有测试已实现；每次报告填入实际测试路径、命令与结果。

| 不变量 | 最小验证场景 | 用户验收 |
|---|---|---|
| 市场日期不受机器时区影响 | 同一固定输入跨 UTC、上海、纽约时区；含午夜和夏令时边界 | 日期与研究结果一致 |
| 未完成与完整周期分开 | 午休、收盘前后、假期及供应商延迟输入 | 结果说明使用到哪个时点及周期状态 |
| 失败、空、部分、过期可区分 | 故障注入、确认空响应、批量缺失、保旧缓存 | 不显示伪零值或伪最新值 |
| 更新与 fallback 不改口径 | 重复回填、部分写入、并发、混合复权和单位 | 数据不丢失；不兼容输入披露或拒绝 |
| 未来信息不影响当前决策 | 修改/追加决策后数据；固定既往可见版本 | 既往信号与资金分配不变 |
| 比较条件一致 | 不同末日、窗口不足、缺失标的、样本池变化 | 排名范围、共同窗口与限制可理解 |
| 资金与绩效口径成立 | 手算重叠持仓、延迟平仓、成本及收益入账 | 汇总可复核，简化模拟准确命名 |
| 安装升级与版本绑定成立 | 临时环境固定版本安装、资源检查、解析失败、迁移中断 | 版本可核对，用户数据可恢复 |
| 重要结果可以复核 | 同一输入快照与参数重放 | 结果一致或差异有明确原因 |

只运行与风险有关的验证并完成项目规定检查；扩大测试须有未解决的问题或新的变更依据。
记录 before/after、运行环境、通过/失败/未运行、覆盖边界及剩余不确定性。
代码检查、离线回放、真实网络可用性与用户验收不能互相替代。

测试夹具纪律：夹具时间戳禁用 naive datetime 与 `ts[:10]` 之类的字符串切片取
日期——前者按机器时区解释、后者把 UTC 前一天切进断言，都会制造「只在本地
通过」的绿灯。夹具一律带显式时区（aware UTC 或 `+08:00`），交易日口径经
`market_data/time_utils` 的工具推导而非字符串运算；修复存量夹具从被触碰文件
里最明显的示范点入手，不做全仓清扫。

## 6. 交付与记录模板

第一轮可合并成一份审查报告和一份实施方案，不强制拆成六份重复文档。
一次性记录放在 `docs/archive/YYYY-MM-DD-<scope>-review.md`；设计方案和验证记录可附在同一文件
或用同前缀独立文件。长期有效原则留在本指南；产品方向不由审查报告自行定义。

报告最少包含：

1. 用户目标、基准版本/commit/工作区与范围。
2. 实际调用链和四领域覆盖摘要；排除项及未验证项。
3. 按证据状态区分的发现清单与根因。
4. 必要契约和方案取舍；旧数据、公开接口及已有结果的影响。
5. 按用户风险与依赖排序的阶段计划；每阶段有用户产物与验收。
6. 不变量 → 测试 → 用户验收矩阵。
7. 验证结果或待执行计划、剩余问题与不确定性。

交付时明确：完成了审查、完成了修复验证，还是仅落地了规范。
“未发现问题”只能用于实际审查范围，不能据此宣称全系统可信或策略有效。
